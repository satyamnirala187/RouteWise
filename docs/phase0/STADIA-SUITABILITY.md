## 1. Two-wheeler profiles on the matrix endpoint (verified on the matrix schema itself)

`POST /matrix/v1` takes `costing: matrixCostingModel`. That enum is defined separately from the route endpoint's, and it includes **`motor_scooter` and `motorcycle`**: auto(+traffic variants), bus, taxi, truck, bicycle, bikeshare, motor_scooter, motorcycle, pedestrian, low_speed_vehicle.

The matrix `costing_options` schema has `motor_scooter` options (`use_primary`, default 0.5; `use_hills`) and `motorcycle` options (`use_highways`, default 1.0; `use_trails`). Both inherit the auto options. Upstream Valhalla marks `motorcycle` **BETA**; `motor_scooter` is not beta and models mopeds, with a 45 km/h default top speed.

Response: `sources_to_targets` is row-ordered, made of `{from_index, to_index, distance, time}`. `distance` is in `units` (default kilometers); `time` is integer seconds; **both are `null` when no route was found**. HTTP 400 is returned when no suitable road edge is found near a location.

Not verified: how well these profiles reflect real two-wheeler access in the test area. That needs a live check.

| Rate limits | Not published ("may limit" abusive use) |

**Batching:** on Standard, split the matrix into tiles of ≤ 25 × 25. Tiling adds no billable elements, because the tiles partition origins × destinations exactly. Requests per initial plan:

| Locations | Tiles |
|---|---|
| 25 (20 orders) | 1 |
| 57 (50 orders) | 9 |
| 110 (100 orders) | 25 |

Each reroute is one request (≤ 81 elements). The adapter enforces the element limit and checks the 200 km span before sending anything.

## 4. Storage: our data versus provider-returned data

| Data | Origin | Where it lives | What the terms say | Status |
|---|---|---|---|---|
| Customer name, contact, products, instructions | **Ours** (Excel/admin) | Our DB; rider device | Never sent to Stadia. §10: Stadia claims no ownership of submitted content | **OK** |
| Order pins (lat/lng) | **Ours** (import/manual pin) | Our DB; rider device | Sent to Stadia as request inputs only. Coordinates of a customer address can be personal data, so the DPA applies | OK; the owner should review the DPA |
| Order assignment and sequence | **Ours**, computed by our OR-Tools solver using matrix values as input | Our DB; rider device | Not addressed. It isn't a Stadia result, but it is derived from one | **Unresolved** (ask) |
| Matrix distances/times | **Stadia** | Should only be in memory during a solve | §8: "proxying or caching access to our Services in any way … (server-side caching is prohibited)"; "creating derivative databases by systematically extracting…" | **Do not persist.** The adapter keeps them in memory only |
| Route totals and ETAs we display (sums of Stadia values) | Derived from **Stadia** | Plan record; admin view; rider device | Not addressed. The 11-09 terms add an explicit permanent-storage right for **geocoding** results only (§30.4), not for routing | **Unresolved** (ask) |
| Snapped coordinates in the response | **Stadia** | Not stored | As above | Not stored |
| Offline rider list | Our data, plus optional Stadia-derived ETAs | Rider device, ≤ 18 h (proposal) | The client-cache exception covers caching "local to the client device", ≤ HTTP cache headers or 7 days. Our list is served from **our** server, so it isn't a direct client cache | **Unresolved** for any Stadia-derived values; our own data is OK |
| Test evidence | Stadia responses | — | The recorded-fixture approach used for OSRM would be server-side storage | **Store metadata only** (`stadia-check` does this) |
| Comparing Stadia's routes with OSRM/Google | — | — | §8 prohibits "**benchmarking** any of our Services against competitor services … without explicit written permission" | **Blocked without permission.** The side-by-side quality test I proposed earlier needs written consent |

**Design consequence (corrected):** storing our computed sequence and assignment is **unresolved**, not permitted by default. Without Stadia's written confirmation, nothing derived from a Stadia matrix may be persisted: not the sequence, assignment, totals or ETAs, server-side or in the offline list. Only our own customer and order data may be stored. In practice that means Stadia cannot back RouteWise's versioned plans (Phase 2) or the offline rider list (Phase 5) unless Stadia answers yes. The enquiry below remains a draft and is relevant only if Stadia is reconsidered.
