## 1. What it does

**Admin (Orders page, API):**
- **Suggestions:** orders with an identical pin show "Same pin as RW-…" (order codes only, never coordinates). The "Same-building stops" panel lists each suggestion with a **Group as one stop** button, and each group with an **Ungroup RW-…** button per member.
- **Group ids** are generated by the server (random, opaque) and never sent to riders. A client cannot choose or reuse one.
- **Atomic and versioned:** a request lists `{id, version}` for every order. It is applied completely or not at all. Refusals: not in this round (404), stale versions, a group that would be split (409), invalid location, pins that differ, too few or too many orders (422).
- **Pin edits:** a manual pin or link edit that **actually changes** the pin takes the order out of its group, with a notice. Re-applying the same pin keeps the group.
- **Singletons dissolve:** a group left with one order is removed, both on ungrouping and on a pin change.
- **Grouping never changes** a status, customer detail, owner lock, first-delivery flag or assignment. Only `building_id` and the order's `version` move (every order edit bumps its version). Tests compare every other column before and after.
- **Messages:** conflicts say what changed and that nothing was saved, with a reload button. A pin edit that removes an order from its group says so and names any order freed with it.

**Planning and rerouting (admin round plans and a rider's own reroute use the same planner code):**

| Situation | Result |
|---|---|
| A confirmed group, enough capacity | **One stop** per applicable rider, holding every customer; **capacity counts each order** |
| Group larger than the rider it must fit (the largest capacity, or its locked owner's) | Split into chunks of that size, **no order dropped or reassigned**; each rider that gets a chunk has one stop at the building |
| Orders of one group with **different owner locks** | One stop per lock; every lock is respected |
| A group's orders with and without a lock reach one rider | They are **one stop** (a later chunk joins the first), never two |
| Group has first-delivery orders | **One priority stop**; priority customers are listed first within it. Two priority customers in one group are not a conflict |
| One customer is completed or postponed | Nothing else changes (versions and statuses of the others are compared). The remaining **Pending customers stay one stop** |
| A Postponed order returns to Pending | It stays outside the saved sequence until the next plan or reroute, then rejoins its group (nothing is reinserted automatically) |
| A rider's reroute | Groups only that rider's **own Pending orders**; another rider's order at the same building is never loaded, moved or shown |
| Groups cannot be packed into the capacities without splitting | The run fails with `NO_FEASIBLE_PLAN` and a hint to ungroup; **nothing is split to make it fit** (limitation 3) |

**Immutability and staleness:**
- A group change is an admin order edit: the round's `input_version` and `route_version` move once per request. In-flight admin solves **and** rider reroutes end `stale` (`INPUTS_CHANGED`), the saved plan reports **out of date**, and reroutes are refused until the admin re-optimizes.
- Saved plans, plan orders, assignments and rider revisions are **never edited** by a group change (all compared row by row). A later plan supersedes, and version 1 stays exactly as saved.
- `building_id` is part of both fingerprints. A test changes membership **behind the API without a version bump** to prove the fingerprints themselves catch it.

**Rider contract (API only):** each stop in `GET /api/rider/rounds/{id}/deliveries` adds `customers` (this rider's Pending customers there now), `shared` (the stop belongs to a group in which this rider holds two or more orders), `location` (**one validated pin** for the whole stop, or null with `location_issue` if the customers no longer share a valid pin) and the within-stop order (first-delivery customers, then order code). The customers keep their own order records and statuses. The existing rider screen shows them as separate cards, as before.

## 3. API

**Admin:**

| Endpoint | Purpose |
|---|---|
| `GET /api/admin/rounds/{id}/stop-groups` | Groups and same-pin suggestions (codes, statuses, versions; no coordinates) |
| `POST /api/admin/rounds/{id}/stop-groups` | `{"orders": [{"id","version"}…]}` makes exactly these orders one stop. Returns `changed`, the group's codes and the updated orders. 404 `NOT_IN_ROUND`; 409 `STALE_ORDERS`, `GROUP_INCOMPLETE`; 422 `LOCATION_NOT_VALID`, `PINS_DIFFER`, `GROUP_TOO_SMALL`, `DUPLICATE_ORDERS`, `GROUP_TOO_LARGE` (over 100 in a request) |
| `DELETE /api/admin/orders/{id}/stop-group` | `{"version"}` takes one order out; a group left with one order dissolves. 409 `STALE_ORDERS`, `NOT_GROUPED` |

- **Replace, not patch:** a request makes *exactly* the listed orders one group with a fresh id. An existing group that a listed order belongs to must be listed completely (`GROUP_INCOMPLETE` otherwise), so a group is never split silently. Submitting a group as it already is changes nothing (`changed: false`).
- Every admin order response adds `stop_group` and `same_pin_as`. `POST …/pin` and `POST …/location-link` add `stop_group_notice` and `stop_group_freed` when they took the order out of a group.
- The admin plan view lists customers within a stop first-delivery first (current plan only; history is reported as saved).
- **Admin only, CSRF and Origin enforced.** The existing route-inventory tests cover the new routes (401 anonymous, 403 for riders, CSRF on every mutation), and a dedicated test covers a foreign origin.
- **Rider:** stops add `customers`, `shared`, `location`, `location_issue`; nothing else changes, and the group id is never sent.

## 4. Versions and locking

- **One lock order:** group create, group removal and a pin edit of a grouped order lock **all the order rows they may touch** (`FOR NO KEY UPDATE`, ascending id, one statement, like the bulk owner lock), and only then update the round row. That is the documented order-edit order (order rows, then round), so there is **no new wait cycle**. Plan commits never lock order rows.
- **Why no extra lock:** the set to lock is read just before locking it. That is safe because a group never gains a member without its id changing: forming or extending a group gives **every member a fresh id and a new version**, so a request made from an older view fails the version check on a listed order, and rows are re-read under their locks before any rule is applied. (I first built a per-round advisory lock, then removed it: the version checks already cover every case, and no test could show a need for it.)
- **Round bump:** once per request (`input_version` and `route_version`). The round-wide invalidation is the existing conservative default (Q4-5), not new.
- **No partial updates:** every refusal happens before any write. A refused request changes nothing, including versions.

## 7. Limitations

1. **No rider shared-stop screens (4D).** The rider page shows each customer as its own card with its own Navigate; the one-Navigate-per-shared-stop presentation, grouped cards and the "N more customers at this stop" wording are 4D. The metadata exists only in the API.
2. **The rule is a provisional default.** Identical pins may be different buildings (for example a campus-wide place link), which is why confirmation is required. Grouping is an extra admin step.
3. **A group is split only for capacity or locks, never to make packing fit.** For example, groups of 4, 3 and 3 cannot fit two riders of capacity 5 although splitting could; the run fails with `NO_FEASIBLE_PLAN` and a hint, and the admin ungroups one. An infeasible search runs to its time limit (2 s in the test; **30 s per strategy, up to three, by default**).
4. **Conservative invalidation (Q4-5 default):** a group change makes the saved plan out of date for every rider and blocks all reroutes until the admin re-optimizes. Admin replanning mid-round (Q1, pending) can still move Pending orders between riders.
5. **Exact equality** is on stored coordinates. Two links that resolve a hair apart are different pins; the admin can set one pin manually to match.
6. **Any status can be grouped through the API** (a Completed order too); the suggestions leave Completed orders out. Grouping never changes a status either way.
7. **Within-stop order is derived** (first-delivery customers, then order code), not stored in `plan_orders`, and for a history plan only the code order is shown.
8. **A group version bump** means an open rider status update for a grouped order may get the existing "changed since you loaded it" conflict and a refresh. Nothing is overwritten.
9. The panel's last confirmation stays visible until the next action (cosmetic).
10. **The database cannot enforce "two or more members, identical pins"**; the API does, and the planner and rider view tolerate a stray singleton (it is not a group) and self-heal it on its next pin edit.
11. **Not checked on a device.** Phone GPS has not been tested (unchanged), and no phone was involved in 4C.
12. **`routewise_phone` is still on schema 0004.** The launcher refuses it and prints the steps; the owner runs `phone_db.py upgrade` (it applies 0005 and 0006, keeping the data). Q4-6 (phone secure context) is still pending.

## 10. Final correction (20 October 2026): reload confirmation

**The defect (mine, in the §9 work).** After "Could not confirm the change", `StopGroups.reloadFromServer` wrote "Reloaded: these are the groups the server has now." and removed the reload button immediately, before the refresh had finished. A failed reload therefore showed a false success and left no way to try again.

**The fix (`pages/OrdersPage.tsx`).**
- `refresh` now returns what happened to the data on screen: `applied` (this round's data loaded), `failed`, or `obsolete` (another round was selected). A request overtaken by a newer one for the same round reports what the newer one produced. A late answer for a round that is no longer selected is dropped as before.
- The panel shows a loading state ("Reloading the current groups…") while the read runs, and the group buttons are disabled meanwhile.
- "Reloaded: these are the groups the server has now." appears **only** when the refresh of the selected round was applied. If it fails, the earlier warning ("Could not confirm the change. Reload to check the current groups.") and the reload button stay, so the read can be repeated any number of times. The change is never sent again: only the reads are repeated.
- If another round is selected meanwhile, the old panel is gone and nothing from that reload is shown on the new round.
- One small related behaviour: a successful refresh now clears the page-level "Could not load orders." message. Without it, a failed read followed by a successful retry would leave a stale error on screen.
